# 直连桥单实例路由架构设计（v1.1）

> 本文是**设计决策记录**：为什么这样设计、评审发现的问题与处置。
> 系统怎么用、出问题怎么查 → 见仓库根目录 `README.md` 和 `docs/排错手册.md`。
> 完整实现架构（组件图/配置清单/验收基线）→ 见 `docs/直连模式整体实现架构.md`。

## 一、背景与问题

### 1.1 演进历程

| 阶段 | 架构 | 结局 |
|---|---|---|
| 第一代 | 轮询机器人（Python 脚本轮询 Chatwoot API） | 因与后续系统双回复冲突，已下线（launchd bootout） |
| 第二代 | FastAPI 通道层 + 智谱直连 + OpenClaw 影子 | 完成使命后退役（代码归档于 chatwoot-legacy 仓库） |
| **第三代（当前）** | **AgentBot 回调 → 直连桥 → OpenClaw** | 生产运行 |

### 1.2 为什么当前采用 AgentBot 回调 + 桥（而非其他方案）

Chatwoot 对接外部 AI 有三种官方/可行方式，经实践评估：

| 方式 | 评估 | 结论 |
|---|---|---|
| **AgentBot 回调**（现用） | Chatwoot 原生机制，按 inbox 绑定，自带 pending→open 人工 handoff | ✅ 采用 |
| 账户级 Webhook | 之前用过，但删除/重建/与 AgentBot 并存时容易出现双触发 | 已替换 |
| OpenClaw Channel 插件 | 需按 mattermost 模板开发 ~1000 行 TS，维护成本高 | 备选未启用 |
| Chatwoot → n8n → OpenClaw | 引入 n8n 依赖 | 备选未启用 |

### 1.3 为什么桥是独立文件而非复用 FastAPI

FastAPI 通道层承载了双引擎/影子测试等复杂逻辑（约 2000 行 + SQLite 三表）。
直连模式只需「验签→路由→转发→回复」约 300 行，独立成文件后：
- 部署单元清晰（launchd 一个服务）
- 故障排查点唯一
- FastAPI 可完整退役随时回滚（plist 保留）

## 二、核心设计决策（与原因）

### 2.1 单实例多收件箱（而非每品牌一个实例）

- 每品牌一个进程：进程数/日志/防火墙随品牌线性增长
- 单实例 + `INBOX_ROUTE_MAP` 路由表：进程恒定 1 个，加品牌=改配置热重载
- 明确代价：**SPOF**（单点故障影响全部品牌）——用 launchd KeepAlive + 兜底机制缓解，
  水平扩展（共享去重/分布式锁）列为 Phase 3+，单实例未到瓶颈前不做

### 2.2 验签：双格式自适应（重要，踩过坑）

Chatwoot 有**两种签名格式**（源码 `/app/lib/webhooks/trigger.rb` 确认）：

| 回调类型 | 签名内容 | 头 |
|---|---|---|
| AgentBot 回调（当前主链路） | `HMAC(bot_secret, "{timestamp}.{body}")` | `X-Chatwoot-Timestamp` |
| 账户级 Webhook | `HMAC(secret, body)` | 无时间戳头 |

桥**两种都验**（候选依次比对，恒定时间比较）。同时 secret 也分两种来源
（bot 自己的 secret / 账户级 webhook secret），因此 secrets 池存多个候选。

**血泪教训**：曾因只实现纯 body 格式 + secret 配错，导致 AgentBot 投递全部 401、
Chatwoot 自动把会话转 open，浮窗整体瘫痪 2 小时。

### 2.3 有界并发与降级三件套

无界并发会在高峰期压满 Gateway。设计：
- 全局并发 4 / 每品牌 2 / 队列 100 / 同会话排队 60s
- 触发降级（队列满/排队超时）→ 三件套：兜底文案 + pending→open 转人工 + 私有备注
- AI 失败时同样走三件套，客户永远有响应，人工永远有上下文

### 2.4 事件流三重过滤与迟到丢弃

OpenClaw WS 事件流必须按 `runId` 过滤（多会话共享连接时防串扰）；
assistant 帧三种语义都要处理：`delta` 追加 / `text` 快照覆盖 / `replace` 替换。
**超时已兜底的消息，后续到达的 AI 回复一律丢弃**（否则客户先收兜底再收迟到回复=双回复）。

### 2.5 路由热重载

SIGHUP 或 60s 轮询 routes.json mtime。加品牌零重启零丢失。
否则每次加品牌重启进程 = 重启瞬间到达的消息丢失 + 处理中回复中断。

## 三、隐藏问题清单（评审发现的 13 项及处置）

| # | 问题 | 处置 |
|---|---|---|
| 1 | 单实例=SPOF | §2.1 声明边界，水平扩展列 Phase 3+ |
| 2 | 无界并发压垮 Gateway | 有界并发+队列 |
| 3 | 事件流只拼接 delta（漏 replace/快照/跨会话串扰） | 三语义+三重过滤 |
| 4 | convId 与 botToken 契约不明 | 启动校验路由 token |
| 5 | 兜底后无人接手 | 转人工+私有备注 |
| 6 | 端点泄露 token/正文 | /stats loopback、日志脱敏 |
| 7 | 验收只有 P50 | P95/P99/迟到回复=0 等完整指标 |
| 8 | 去重进程内不持久 | JSONL 水位持久化+启动恢复 |
| 9 | 重启丢消息 | 恢复扫描+告警备注（不自动补发防双回复） |
| 10 | 兜底风暴（Gateway 故障时全部客户收重复机械文案） | 分品牌限流 |
| 11 | 未映射 inbox 静默失联 | 降级三件套含私有备注 |
| 12 | 统计重启归零 | 落盘 |
| 13 | 加品牌需重启 | 热重载 |

## 四、已知限制与运维规律（必须知道）

### 4.1 AgentBot 只处理 pending 会话

- 新会话自动 pending（bot 负责）
- bot 回调失败 → Chatwoot **自动转 open**（防客户干等）→ **bot 不再处理该会话**
- 人工接管 = open；人工完毕想让 bot 继续 = 手动切回 pending
- **排错口诀：浮窗某会话不回复而其他正常，第一件事查会话状态是不是 open**

### 4.2 Chatwoot 的 PUT /inboxes/{id} 会静默清空 agent_bot 绑定

修改 inbox 用 PATCH，或 PUT 后重新绑定。绑定关系存于 `agent_bot_inboxes` 表
（含 status 字段，active 才投递）。

### 4.3 两个 secret 容易搞混（见 §2.2）

**排错口诀：日志大量「验签失败」= secret 池缺当前投递方使用的 secret**。
从 Chatwoot API 读各 bot 的 secret 补进 routes.json。

### 4.4 改代码/配置必须重启桥（或等热重载）

曾因此排查 2 小时（旧进程跑旧逻辑）。launchd 服务改 plist 后需 bootout+bootstrap。
