**版本**：v1.1（合并架构评审 7 项修订）
**日期**：2026-11-17
**状态**：待批准
**前置**：Chatwoot ↔ OpenClaw 直连桥已在生产运行（BlueWMS 8300 / 卓风 8301 双实例模式）。

**v1.1 修订说明**：采纳评审意见——①架构目标重命名为「单实例多收件箱」并声明单点故障边界；②新增并发与队列控制章节；③新增事件流关联规范；④明确 convId/botToken 契约；⑤兜底联动人工接手；⑥端点安全；⑦验收指标修订（P95/P99/迟到回复/兜底率定义）。另合并内部排查发现的 4 项隐藏问题（持久化去重/重启恢复/兜底风暴限流/路由热重载）。全部为**方案修订，不含代码修改**。

## 一、背景与问题（沿用 v1.0）

多端口多实例模式（每品牌一个 bridge 进程/端口/plist）随品牌数增长产生线性运维负担：进程数、日志组、防火墙规则、配置漂移、端口表管理。需要收敛为单实例动态路由架构。

## 二、架构目标与边界（v1.1 修订）

### 2.1 架构定位（重要声明）

| 项 | 定义 |
|---|---|
| 本方案目标 | **单实例多收件箱**（Single-Instance Multi-Inbox）：一个进程承载全部品牌，运维对象恒定 |
| **本方案不是** | 水平扩展设计。单实例是**单点故障（SPOF）**：进程崩溃 = 全部品牌停止回复（直至 launchd 拉起，约秒级） |
| 可用性兜底 | 进程崩溃期间到达的客户消息由 launchd 拉起后恢复处理；兜底文案机制保证崩溃前已受理消息有响应 |
| 水平扩展 | **列为后续架构阶段（Phase 3+）**，前置条件见 §13。启用前需：共享持久去重状态（SQLite→Redis/DB）、分布式会话锁或按品牌分队列、消息队列化（消费者分区） |

### 2.2 SPOF 影响评估（诚实声明）

| 故障 | 影响半径 | 恢复 |
|---|---|---|
| bridge 进程崩溃 | 全部品牌停止回复 | launchd KeepAlive 秒级拉起；**崩溃前处理中的消息可能丢失**（§9 重启恢复缓解） |
| OpenClaw Gateway 故障 | 全部品牌走兜底文案（故障域合并——双实例模式下只影响单品牌） | 兜底风暴限流（§5.4）+ 熔断；Gateway 恢复后自动回归主链路 |
| 206 主机断电/断网 | 全部品牌 + main 助理全停 | 依赖主机可用性（与现状相同） |

### 3.2 路由配置

```bash
# inbox → {agentId, botToken}；botToken 必须是 Agent Bot Access Token（§6 校验）
INBOX_ROUTE_MAP={"7":{"agent":"bluewms-support","botToken":"<客服Agent token>"},
                 "8":{"agent":"zhuofeng-support","botToken":"<卓风Agent token>"}}
# 验签 secret 列表（覆盖全部bot 回调使用的 secret；当前生产为单一账户级 secret）
WEBHOOK_SECRETS=["<secret>"]
```

### 3.3 新旧模式对比

| 维度 | 旧（多实例） | 新（单实例路由） |
|---|---|---|
| 进程数 | N（随品牌增长） | **1（恒定）** |
| 新品牌接入 | plist + 端口 + 防火墙 + 重启 | 改路由表 + 重启（后续支持热重载 §11） |
| 端口 | N 个 | 1 个（8300） |
| 故障半径 | 单品牌 | 全品牌（SPOF，§2.2） |
| 观测 | 无 | /healthz + /stats（loopback 限制 §8） |

## 四、并发与队列控制（v1.1 新增）

### 4.1 问题

当前实现为**无界并发**：每条消息到达即发起 OpenClaw 调用，高峰期多品牌消息同时涌入会压满 Gateway/模型服务。

### 4.2 控制参数（有界化）

| 参数 | 默认值 | 依据 |
|---|---|---|
| 全局并发上限 `MAX_GLOBAL_CONCURRENCY` | 4 | 实测 glm-5.3-Flash 单会话 5-30s，Gateway 同时 2-3 会话流畅，4 保守 |
| 每品牌并发上限 `MAX_PER_INBOX_CONCURRENCY` | 2 | 防止单品牌占满全局额度 |
| 全局队列容量 `MAX_QUEUE_SIZE` | 100 | 超出直接降级（见 4.4），防止内存无限增长 |
| 会话串行等待上限 `SESSION_QUEUE_TIMEOUT` | 60s | 同会话排队超过 60s 未处理 → 降级（见 4.4） |

### 4.3 队列/降级行为定义（每条路径明确）

| 场景 | 行为 |
|---|---|
| 队列已满（新消息无法入队） | ① 发兜底文案 ② Chatwoot 会话加**私有备注**（含原因）③ 状态 pending→open 转人工 ④ ERROR 级日志 |
| 同会话排队超 60s | 同上（说明前序消息处理异常堆积） |
| 全局并发满但队列有空位 | 消息入队等待（客户等待时间增加，不降级） |
| OpenClaw 调用超时（30s） | 兜底文案 + 转人工（§7） |

### 4.4 降级动作组件

「兜底文案」升级为「降级三件套」：兜底文案（客户可见）+ 私有备注（工作台可见，含失败原因/时间戳）+ 状态转 open（人工接手信号，仅 AgentBot 模式下 pending 会话需要）。

## 五、OpenClaw 事件流关联规范（v1.1 新增）

### 5.1 已验证的帧语义（实测）

| 帧 | 语义 | 处理 |
|---|---|---|
| `res`（对应 req id） | RPC 响应（sessions.create/send） | 按 id 匹配 pending 表 |
| `event=agent, stream=assistant, data.delta` | **追加片段**（首帧含 `{text, delta}`，后续仅 `{delta}`） | `text += delta` |
| `event=agent, stream=assistant, data.text`（无 delta） | 全量快照 | `text = data.text`（覆盖） |
| `data.replace=true`（协议支持） | **替换当前文本** | `text = data.delta`（替换，不追加）——**v1.1 新增处理** |
| `event=agent, stream=usage` | token 用量 | 记录 |
| `event=agent, stream=lifecycle, data.stopReason` | 本轮结束 | 完成收集 |

### 5.2 多会话隔离规则（v1.1 强制）

单 WS 连接承载多会话（不同品牌/不同客户并发）时，**所有事件帧必须三重过滤**：

1. `payload.runId === 本轮 runId`（缺失 runId 的帧丢弃）
2. 事件监听器按会话注册/注销（本轮结束即移除 collector，防跨轮污染）
3. 断言 `payload.sessionKey`（如协议提供）与会话 key 一致

**禁止**：全局单变量收集、跨 runId 复用 collector。

### 5.3 迟到回复丢弃语义

超时已兜底的消息，其后续到达的 OpenClaw 回复（含 stopReason 帧）**必须丢弃，绝不补发**——否则客户先收兜底文案再收迟到回复 = 双回复（红线）。实现：超时即移除 collector 并标记 runId 为放弃。

## 六、写回 API 与身份契约（v1.1 新增）

| 项 | 契约 | 校验方式 |
|---|---|---|
| convId | Chatwoot webhook payload 的 `conversation.id` 即写回 API 的 conversation_id（`POST /api/v1/accounts/{id}/conversations/{convId}/messages`）——两者为同一标识 | 实测已验证（504/507 等真实消息回写成功） |
| botToken | 路由表中的 token **必须是 Agent Bot Access Token**（Settings→Bots 生成的 access_token），**不是**普通 User Access Token | 启动时校验：对每条路由的 token 调用 `GET /api/v1/accounts/1/agent_bots` 核对存在性与匹配性；不匹配则拒绝启动该路由并 ERROR 日志 |
| secret | webhook 验签 secret 为账户级/或 bot 级（以 Chatwoot webhook 配置页显示为准） | 与 WEBHOOK_SECRETS 列表比对 |

## 七、兜底与人工接手（v1.1 新增）

### 7.1 兜底完整动作序列

```
触发（超时/失败/队列满）：
  1. 发兜底文案给客户（文案明确"人工稍后跟进"）
  2. Chatwoot 会话状态：pending → open（人工接手信号；仅 AgentBot 绑定模式下 pending 会话需要）
  3. 可选：会话分配给指定团队/坐席（配置项，默认不分配只转 open）
  4. 私有备注写入失败原因（工作台可见，人工接手时有上下文）
  5. ERROR 级日志（含 msgId/品牌/原因/时延）
```

### 7.2 人工接手语义

| 场景 | 行为 |
|---|---|
| AgentBot 模式（inbox 绑定 bot，会话 pending） | 兜底时必须转 open——否则会话停留在 pending，人工看不到、客户不知道谁处理 |
| 账户级 webhook 模式（会话直接 open） | 状态已是 open，仅加私有备注 |

## 八、安全：端点与信息泄露防护（v1.1 新增）

| 端点 | 暴露内容 | 防护 |
|---|---|---|
| /healthz | 进程存活、Gateway 连接态、路由就绪摘要（inbox→agent 名称，**不含 token/secret**） | 可暴露给内网监控 |
| /stats | 按 inbox 聚合：处理数/成功率/兜底率/时延分位 + 熔断状态。**不含** bot token、secret、客户消息正文、session_key 全文 | **仅监听 loopback**（127.0.0.1），不进入局域网 |
| 日志 | 含 msgId/会话 id/时延/错误；**客户消息正文截断至 30 字符**且不记录回复正文 | 日志文件权限 600 |

统计持久化：/stats 数据落 SQLite（`stats_daily` 表），进程重启不归零。

## 九、持久化与重启恢复（v1.1 新增，修复 SPOF 缺陷）

| 机制 | 设计 |
|---|---|
| 去重持久化 | message_id 水位 + 处理状态落 SQLite（表 `processed_messages`）；重启时加载近 24h 水位，Chatwoot 重试投递不会重复处理 |
| 重启恢复扫描 | 启动时扫描「处理中」状态且超过 5 分钟的消息记录 → 告警日志 + Chatwoot 私有备注（提示人工该条可能未回复）；**不自动补发**（防迟到双回复），由人工决定 |
| 兜底限流 | Gateway 故障时兜底文案按品牌限流（每 inbox 每分钟最多 3 条兜底文案，超出的消息只加备注不发文案），防止单点故障演变为向全部客户发送重复机械文案的风暴 |
| 路由热重载 | 支持向进程发 SIGHUP 重读路由表（或轮询配置文件 mtime），**加品牌不再重启进程**（消除重启丢消息窗口） |
| 内存水位 | 去重表/锁表/队列长度进 /stats，超阈值告警 |

| 端点/日志 | 内容 |
|---|---|

## 十二、验收标准（v1.1 修订）

| # | 指标 | 目标 | 说明 |
|---|---|---|---|
| 1 | 进程数 | 恒定 1，不随品牌增长 | |
| 2 | 时延（分品牌统计） | P50 ≤ 10s；**P95 ≤ 25s；P99 ≤ 30s**（超过 30s 应已兜底，P99 不应出现裸超时） | 观察 7 天 |
| 3 | 兜底率 | **分母 = 观察期全部客户消息数（含降级）；目标 ≤ 5%；观察期 7 天**（依据：beta 实测 3.0%，留工程余量） | 按品牌分列 |
| 4 | Gateway 断线恢复 | 断线期间 100% 兜底；恢复后 60s 内主链路回归（探测通过） | 故障演练 1 次 |
| 5 | 重复事件率 | 0（Chatwoot 重试/重启场景不重复回复） | 重启演练 1 次 |
| 6 | 超时后迟到回复 | 0（超时即丢弃，永不补发） | 日志核验 |
| 7 | 降级三件套完整率 | 100%（兜底文案+转人工+私有备注同时存在） | 抽查降级记录 |
| 8 | 红线 | 双发/串线/未授权身份回复 = 0 | 全程 |
| 9 | 新品牌接入耗时 | 改路由表 + 热重载，≤ 1 分钟，零消息丢失 | 接入演练 1 次 |
