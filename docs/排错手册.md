# Chatwoot ↔ OpenClaw 直连桥 — 架构说明与排错手册

> 本文档面向后续接手的开发/运维人员。读完这一篇即可理解系统如何工作、出问题怎么查。
> 更深入的设计细节见《直连桥单实例路由架构设计》。

---

## 一、这个系统是干什么的

客户在官网浮窗发消息，**AI 自动回复**，无需人工介入（需要时转人工）。

```
客户浏览器浮窗
      │ 发消息
      ▼
Chatwoot（客服系统，存储消息/管理会话）
      │ 收到客户消息后，把消息 POST 给下面这个地址（AgentBot 机制）
      │ http://192.168.0.206:8300/webhook/chatwoot
      ▼
本桥接服务（bridge-v11.mjs，就是本仓库）
      │ 1. 验证签名（确认请求真的来自 Chatwoot）
      │ 2. 判断是哪个品牌的消息（按 inbox 编号查路由表）
      │ 3. 去重（同一消息只处理一次）
      │ 4. 调用 OpenClaw 里的 AI Agent 生成回复
      │ 5. 把回复发回 Chatwoot（以该品牌机器人的身份显示）
      ▼
客户在浮窗看到 AI 回复
```

**为什么需要这个"桥"？** Chatwoot 发消息用的是 HTTP，OpenClaw 收消息用的是 WebSocket——
两种协议说不到一块去，桥就是中间的翻译官。OpenClaw 官方不支持 HTTP 收消息，
Chatwoot 也不会说 WebSocket，所以这个翻译层必须存在（但可以很小，本桥仅约 500 行）。

## 二、系统组件清单（都跑在哪）

| 组件 | 位置 | 端口 | 作用 | 守护方式 |
|---|---|---|---|---|
| Chatwoot | 云服务器 124.223.140.242（公司云） | 443(HTTPS) | 客服系统本体 | 云端运维 |
| **bridge.mjs** | **Mac mini B (192.168.0.206)** | **8300** | Chatwoot↔OpenClaw 翻译 | launchd `com.blueaisoft.cw-oc-bridge`（崩溃自动拉起+开机自启） |
| OpenClaw Gateway | 同上 Mac mini B | 18789（仅本机可访问） | AI Agent 运行时（对话/记忆/人设） | launchd `ai.openclaw.gateway` |
| OpenClaw.app | 同上 Mac mini B | — | 图形界面（可选） | 手动 |

### 品牌与 Agent 对应关系（当前 2 个品牌）

| 收件箱 (inbox) | 品牌 | OpenClaw Agent | 回复时显示的身份 |
|---|---|---|---|
| 7 | BlueWMS | `bluewms-support` | 客服Agent（BlueWMS bot 的 token） |
| 8 | 卓风 | `zhuofeng-support` | 卓风Agent（卓风 bot 的 token） |

**加新品牌 = 3 步**（详见《直连桥单实例路由架构设计》）：
1. Chatwoot 后台建 bot + inbox，bot 的 outgoing_url 填 `http://192.168.0.206:8300/webhook/chatwoot`
2. 修改 `routes.json`：secrets 加新 bot 的 secret，inboxMap 加新映射
3. 等桥自动热重载（60 秒内）——**不用重启任何服务**

## 三、关键配置文件

### routes.json（路由表，含密钥，不入 Git）

```json
{
  "secrets": ["<串1>", "<串2>", ...],     // 验签用的 secret 池
  "inboxMap": {
    "7": { "agent": "bluewms-support",  "botToken": "<BlueWMS bot token>" },
    "8": { "agent": "zhuofeng-support", "botToken": "<卓风 bot token>" }
  }
}
```

- **secrets**：Chatwoot 回调时用 secret 做签名，桥验签。每个 bot 有自己的 secret
  （Chatwoot 后台 Settings→Bots 里看，或 API `GET /agent_bots/{id}` 的 `secret` 字段）
- **botToken**：即各 bot 的 access_token（同一页面），桥用它把回复**以该品牌机器人身份**发回
- 修改后 60 秒内自动生效（无需重启）；紧急时 `kill -HUP <桥进程号>` 立即生效

### launchd 服务（~/Library/LaunchAgents/）

| 文件 | 服务 |
|---|---|
| com.blueaisoft.cw-oc-bridge.plist | 桥（本仓库代码） |
| ai.openclaw.gateway.plist | OpenClaw Gateway |

## 四、正常工作时的日志长什么样

`logs/bridge.log`（每条消息 3 行，约 5-15 秒完成）：

```
[INFO] 处理消息 {"msgId":539,"convId":60,"inbox":"7","agent":"bluewms-support"}
[INFO] Gateway 已连接
[INFO] 已回复 {"msgId":539,"latency":4586,"degraded":false,"chars":70,"agent":"bluewms-support"}
```

- `degraded:false` = AI 正常生成；`degraded:true` = AI 失败，给客户发了兜底文案
- latency 超 20000ms 会额外打一条 `慢请求` 告警

## 五、排错手册（按症状查）

> 通用排查三步：`launchctl list | grep bridge` 看进程 → `curl localhost:8300/healthz` 看健康 →
> `tail -50 logs/bridge.log` 看日志。下面按具体症状展开。

### 症状 1：客户发消息，浮窗完全没反应

**按顺序检查：**

1. **会话状态是不是 open？**（最常见！）
   Chatwoot 后台打开该会话看状态。**AgentBot 只处理 `pending` 状态的会话**。
   - 如果是 open → 系统消息 "error with the agent bot" 出现过，说明之前 bot 回调失败，
     Chatwoot 自动把会话转成了 open（防止客户无限等机器人）
   - 修复：API 切回 pending（或后台用 "Open" 按钮旁的状态切换）：
     ```bash
     curl -X POST "https://chat.blueaisoft.com/api/v1/accounts/1/conversations/<会话ID>/toggle_status" \
       -H "api-access-token: <用户token>" -H "Content-Type: application/json" \
       -d '{"status": "pending"}'
     ```
   - 切回 pending 后**下一条客户消息**会重新触发 bot

2. **Chatwoot 的 bot 投递日志有没有报错？**
   ```bash
   ssh mac5@192.168.0.205   # Chatwoot 宿主机（密码见团队内部）
   /opt/homebrew/bin/docker logs chatwoot-sidekiq --since 30m 2>&1 | grep -iE "webhook|fail" | tail
   ```
   - 看到 `401 Unauthorized` → secret 不匹配，看症状 3
   - 看到 `Exception: Invalid webhook URL ... timeout` → 网络不通（桥挂了或 IP 变了）
   - **什么都没有** → Chatwoot 根本没触发投递，检查 inbox 是否绑定了 bot、事件是否 message_created

3. **桥的日志有没有收到请求？**
   - 完全没有新日志 = 请求没到达桥 → Chatwoot 侧投递失败或网络问题
   - 有 `验签失败` = 到达了但 secret 不匹配 → 看症状 3

### 症状 2：客户收到回复但内容是"抱歉，我这边暂时无法回答..."

这是**兜底文案**（AI 失败时的保底响应，属正常降级不属故障）。原因按概率：

1. OpenClaw Agent 超时（>30s）——查 `logs/bridge.log` 的 `慢请求`/`兜底` 条目频率
2. Gateway 挂了 → `curl localhost:18789/health`（应返回 `{"ok":true}`），不行就：
   ```bash
   launchctl kickstart -k gui/501/ai.openclaw.gateway
   ```
3. 模型服务故障（glm-5.3-Flash 上游）→ 等恢复，或临时改 routes.json 换备用模型

频繁出现（>10%）时深入查 Chatwoot sidekiq 日志（同症状 1 第 2 步）。

### 症状 3：日志大量 `验签失败 {"ip":...}`

**secret 不匹配**。三种来源的 secret 容易搞混（血泪教训）：

| secret | 谁在用 | 在哪看 |
|---|---|---|
| bot 自己的 secret（如 `ePanG...`） | **AgentBot 回调签名（当前主链路）** | Chatwoot API：`GET /agent_bots/{id}` 的 `secret` 字段 |
| 账户级 webhook secret（如 `YmAi...`） | 账户级 webhook 回调签名（当前未启用） | Chatwoot 后台 webhooks 设置页 |

修法：把正确的 secret 加进 `routes.json` 的 secrets 数组，等 60s 热重载。
**注意签名格式**：AgentBot/带 `X-Chatwoot-Timestamp` 头的请求，签名内容是 `时间戳.消息体`；
不带时间戳头的是纯消息体。桥已自适应两种，无需手动区分。

### 症状 4：客户收到两条相同/不同的回复

**双回复事故！立即处理：**

1. 看两条回复的 sender 名字是否相同：
   - 相同 → 同一服务发了两次：检查是否有两个 bridge 进程（`pgrep -f bridge` 应只有 1 个）
   - 不同 → 有**另一个机器人**也在回复（如遗留的旧服务、其他集成），查 Chatwoot 后台
     Settings→Bots 的各 bot outgoing_url，以及会话消息详情里的 sender
2. 历史案例：2026-11-16 曾发现 205 上遗留的旧轮询机器人（已下线）

### 症状 5：重启了 Chatwoot/改了配置后，桥一直收不到消息

- **检查 inbox 与 bot 的绑定还在不在**（重要！某些 Chatwoot 操作会静默清掉绑定）：
  ```bash
  # 在 Chatwoot 宿主机执行（读绑定表）
  docker exec chatwoot-web sh -c "cd /app && bundle exec rails runner \
    'puts AgentBotInbox.where(inbox_id: 7).pluck(:agent_bot_id, :status)'"
  ```
  应输出 `[3, "active"]`（bot3 绑在 inbox 7）。若为空或 status 异常：
  ```ruby
  AgentBotInbox.create!(inbox_id: 7, agent_bot_id: 3, status: "active", account_id: 1)
  ```
- **注意**：Chatwoot 的 PUT /inboxes/{id} 接口会**静默清空 agent_bot_id 绑定**——
  永远用 PATCH 修改 inbox，或改完 PUT 后重新绑定

### 症状 6：桥进程反复崩溃（launchd 反复拉起）

```bash
tail -30 logs/bridge.err.log   # 看崩溃原因
```
- `EADDRINUSE 8300` → 端口被占：`lsof -ti :8300 | xargs kill`，然后 launchctl kickstart
- 语法/启动错误 → `node --check bridge-v11.mjs` 本地排查（改代码后忘重启也会出现"改了没生效"）

**血泪教训**：改了代码/配置必须重启桥服务，否则跑的还是旧逻辑（曾因此排查 2 小时）。

```bash

```

## 七、历史事故档案（勿重蹈覆辙）

| 日期 | 事故 | 根因 | 教训 |
|---|---|---|---|
| 11-17 上午 | 浮窗全部不回复 | Chatwoot 迁移配置操作把 inbox→bot 绑定清掉了 + secret 配错 + 改码未重启，三层叠加 | 排障先查会话状态和 sidekiq 日志，别只看桥 |
| 11-16 | 双回复（客户收到两条不同机器人回复） | 205 上遗留旧轮询机器人并行工作 | 下线旧服务要彻底（launchd bootout 而非 kill） |
| 11-16 | 消息处理超时挂死 | Gateway 假死时 WebSocket recv 永不返回 | 全部等待点必须有强制超时兜底 |

**最重要的教训**：改 Chatwoot 任何配置前，先在会话里发测试消息记录当前行为；改完再发一条对比。
测试消息必须**从真实浮窗发**（或模拟完整链路），本机 curl 直接打桥不经过 Chatwoot 网络，会漏掉网络层问题。
